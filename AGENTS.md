# Global guidelines and constraints

## Constraints

- `tasks/` or `local/tasks/`: Read/write for planning. Plans never belong to the code repo: run `git add`/`git commit` on plan files only inside a dedicated plans repo (`tasks/.git`, e.g. `openQA-tasks`), never in the checkout that hosts the directory. Never `rm` a plan file.
- `tasks/` layout: root = active plans; `wip/` = implementation started; `review/` = done, awaiting review; `completed/` = archived; `todo.md` = backlog. Move finished plans to `completed/` with plain `mv` (never `git mv` or `git rm`).
- Plans gated on an external event (PR merge, unmerged dependency, human approval, production window) stay in their lifecycle dir and carry `## Blocked`: condition, read-only verification command, date recorded. A plan with an unresolved gate is not active: run the command, record the result and the date in the plan, then execute. No `blocked/` dir: the dir axis is lifecycle only, and a `wip`-plan can be gated.
- `AGENTS.md`: Do not version control (unless already under version control).
- Never run `git clean` or any command that deletes unversioned files without confirmation.
- Never run any command using `sudo`.
- Commit verified changes before declaring work done; never push, open or merge PRs unless requested. Before any `git commit`, `--amend`, rebase, or conflict resolution, load and follow the `git-workflow` skill (do not commit from memory).

## Agent Guidelines

- **Merge Advice**: Repos here auto-merge through `mergify` or branch protection, so an approved PR with green CI and a clean merge state needs nothing from me: never recommend merging it, and leave a fresh PR to reviewers for several days before chasing approvals. Never run the merge yourself (`gh pr merge`, `glab mr merge`): if the forge does not merge, report the missing condition, e.g. a rule that needs two approvals while only one exists. Report the state plus the single remaining blocker (missing approval, blocking label, conflict, failing check) or "nothing to do"; name an action only when it is human-only (address `CHANGES_REQUESTED`, force-push after a rebase, add a label).
- **PR Follow-Up**: After opening a PR, stay in the session and run `/pr-watch` (`pr-followup` skill) instead of leaving the follow-up to a later session; propose fixes on new feedback, pause for approval unless pre-authorized, and stop at human-only blockers. More than one own PR with open feedback: `/pr-sweep` gives each PR its own worktree and works them one at a time. 
- **Tone & Radical Candor**: Use a concise, pragmatic, low-affect engineering tone (no flattery, praise, superlatives, or marketing-speak). Assume drafts/prompts have gaps; challenge requests that harm system-wide integrity or maintainability, probe edge cases, and prioritize technical depth over quick scripts.
- **Skill Loading**: Proactively load matching domain (`perl-dev`, `python-dev`, `openqa`, `openqa-log-analysis`, `openqa-svirt`, `openqa-llm-investigate`, `leap-sync`) and situational (`git-workflow`, `code-review`, `testing`, `rpm-packaging`, `colgrep`, `redmine`, `suse-it-ticket`) skills from `<available_skills>` via the `skill` tool at task start. `suse-it-ticket` is not in this checkout: it ships outside the repository in `~/.agents/skills/` and covers internal service-desk requests, so load it from there when a ticket has to be filed.
- **Rule Discovery**: At project start, inspect project conventions (`AGENTS.md`, `CONTRIBUTING.md`, `xt/`, `Makefile` targets like `check`/`lint`) and follow them.
- **Continuous Learning**: Proactively suggest `/learn` when identifying reusable optimizations, recurring issues, or workflow improvements.
- **Sub-Agents & Self-Review**: Use `Task` sub-agents for context-heavy research or diff reviews (read-only `explore` agent for file/pattern/constraint research); on non-trivial tasks, run a sub-agent review for maintainability and duplication before finishing.
- **Long-Running Commands**: Run slow commands synchronously in one tool call with an explicit `timeout`; background `nohup … &` launches are killed when the tool call returns, so do not poll for their output in a later call, while a `setsid` launch is its own session and survives: detach a run that must outlive the call with `setsid … &` and tail its log in a later call. External LLM/CI endpoints are often single-slot (`503 server busy`): keep one request per call until that endpoint has proven concurrent, while the helmcode/strata routes carry many pi and opencode sessions at once.
- **Remote Investigation**: Batch read-only probes on a remote host into one `bash` call (`ssh <host> 'a; b; c'` with `BatchMode=yes` and an explicit `timeout`): the round trip dominates, so one call per investigation step, not one per command. Load the matching infra skill (e.g. `openqa-o3-infra`) for host-specific facts, root-only paths and verification actors. `sudo` stays prohibited unless explicitly approved per task; any write on a production host needs approval and is verified with the actor that runs at boot, not with the interactive tool.
- **Proof-of-Work Pages**: `hackweek.opensuse.org` answers plain `curl` with an "openSUSE check" interstitial instead of the page: do not retry it and never summarise the interstitial as page content. Fetch such pages with the unversioned local helper `anubis-get <url>` (`--raw` for HTML) instead of writing a one-off script.
- **Planning & Execution**: When asked for a plan, create only `tasks/<NNN>_<ticket_id>_<snake_case_desc>.md` (or `local/tasks/`), breaking work into atomic, independently committable tasks without modifying other files (`NNN` = max 3-digit prefix across local branches, `tasks/` files, and `tasks/todo.md` + 1, default `001`). Read existing `tasks/` plans fully before starting and re-read after user edits.
- **Session Handoff**: Start execution in a fresh session from the plan's `## Session starter`; the plan file is the interface between sessions. A plan carries `## Approvals` (decision, approver, date), `## Gates` (verification command per commit), and `## Session starter`, and `git status` is read before acting. Use `/handoff` only when no plan file carries the decisions. Approval counts only when the plan records it: never infer it from a previous conversation.
- **Verification**: Every code change must include corresponding test updates or new tests.
- **Code & Comment Style**: Keep code, PRs, issue replies, and reviews brief with minimal blank lines and zero duplication. Prefer self-explanatory names/structure; comment only the _why_ of complex logic, never _what_. In tests, NEVER write in-file comments—always use self-explanatory test description strings. Commit and PR text states only what the diff and CI do not already show: no claim the implementation, a test, or a tool guarantees by definition, no section that restates the diff.

## Vendored skills (opencode + pi, shared via `~/.agents/skills`)

- **Vendored Skills**: curated copies of `mattpocock/skills` + `addyosmani/agent-skills` live in `~/.agents/skills` (whitelist `~/.agents/vendor-whitelist.txt`, refresh `~/.agents/sync-vendor-skills.sh`); upstream clones stay in `~/.local/share/agent-skills`. Load on demand via the `skill` tool or `/skill:<name>`; never edit vendored copies, edit the whitelist instead. A vendored template (e.g. `pr`'s Summary/Evidence/Merge Danger) is a menu, not a repo convention: the repo's own PR layout (repo `AGENTS.md`, PR template, `openqa` skill) wins and sections it does not require are left out.
